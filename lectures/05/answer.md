# 第5回 解答

## 演習

- 回答モデル：`gemini-3.5-flash-lite`
- 比較した質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」
- 対象資料：全文投入は `lectures.json` 内の全9資料438ページ。基本RAG・Tree・Graphは第1〜3回の本講義214ページ。対象資料の範囲が異なるため、方式間の公平な性能比較にはなっていない。
- 埋め込みモデル：`gemini-embedding-001`（768次元）。検索用SQLiteには第1〜3回本講義214ページの本文・属性・埋め込みベクトルを保存。

### 検索だけを実行して見つかったページと、本文で確認できたこと

`uv run python -m app.retrieval "LoRA QLoRA 違い"` の検索結果は次の順だった。

2. 第2回 p.51「PEFT」：LoRAとQLoRAの違いの直接の根拠。

### `--trace`で見えたツール呼び出し

- 全文投入：検索ツールを使わず、全資料本文を227,971文字の入力に結合した。
- 基本RAG：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し、モデルが検索語を作成した。
- Tree：`browse_tree` を4回呼び出した。資料一覧 → `lec02-main` → `lec02-main-s045` → `lec02-main-p052`。末端ページの本文717文字を取得した。目次の候補も入力となるため、トークン数が増えた。
- Graph：`search_graph({'query': 'LoRA QLoRA 固定 学習 第2回'})` を1回呼び出した。入口はp.52、p.60、p.51（いずれも0 hop）。

Graphの追加取得7件と探索経路：

- 1 hop：p.52 → p.53、p.60 → p.59、p.60 → p.61、p.51 → p.50。
- 2 hops：p.60 → p.61 → p.62、p.51 → p.50 → p.49、p.52 → 用語「LoRA」 → p.47。

Graphはあらかじめ定義されたページ間の`next_page`およびページ・用語間の`mentions`をたどっている。最初の入口はベクトル検索だが、その後に広げるページは必ずしも質問との類似度を再評価していない。

### 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例

- 今回の質問では全方式がp.51またはp.52へ到達し、根拠が不足する例は観測されなかった。
- 全文投入では参照ページを特定したが、質問への直接回答ではなくヒントを返した。情報を取得することと回答に利用することは異なる。
- Graphではp.62（AIエージェントへの次回予告）などの不要なページも追加された。p.51とp.52はGraphで増えたページではなく、最初のベクトル検索で既に取得できていた。

### 今回の用途に採用したい方式と改善案

- 今回の質問に限れば、基本RAGを第一候補とする。必要なp.51・p.52を取得し、回答は正しく、入力トークンと生成API推定費用が最小だった。全文投入比で入力トークン数は約97.4%、生成API推定費用は約70.1%減少した。
- 基礎：`RAG_TOP_K`を5から2へ変更し、不要なページが減るか、根拠を取りこぼさないかを比較する。
- 実装：検索ヒットの前後1ページを、同一資料内に限り重複なしで追加取得する。
- 発展：Graphの追加候補を絞る方法を設計し、基本RAGと同条件で比較する。
- 限界：全文投入と他の方式では対象資料の範囲が異なり、各方式1回・1質問だけの実験である。速度や正答率の一般的な優劣は断定できない。埋め込み費用は見積もりに含まれていない。

### 気づき・疑問

ベクトル検索では「質問と似たページ」を探すが、Treeは「資料の階層」、Graphは「前後ページや共通用語の関係」をたどる。取得件数が多いほど良い回答になるとは限らず、どの追加情報が実際に回答を裏付けたかの確認が必要である。

### 発展（完了）：Graph検索の候補選択を改良

#### 目的と変更内容

- 変更ファイル：`app/retrieval.py`
- 目的：Graphが追加する不要なページを減らし、必要な根拠を維持する。
- 元のデータ構造：`graph.json` のページ・用語ノードと、
  `next_page`・`mentions` の関係。
- 探索方法：ベクトル検索で入口3ページを選び、
  Graphで最大2 hopまで探索する。
- 改良方法：追加候補を質問中の語とタイトル・本文との一致で採点。
  タイトル一致を高く評価し、関連候補を最大3ページ返す。
- `AIE_GRAPH_FILTER=1` で改良版を有効化。
- 追加の埋め込み索引作成は不要。

#### 検索結果の比較

検索語：`コンパクション セッション 長期メモリ 第3回`

| 項目 | 従来Graph | 修正版Graph |
|---|---:|---:|
| 入口ページ | 3 | 3 |
| 追加ページ | 7 | 3 |
| 合計ページ | 10 | 6 |
| 重要な第3回p.40 | 取得 | 取得 |
| ページ重複 | なし | なし |

- 改良前の失敗：最初のフィルタでは追加ページが0件となり、
  重要な第3回p.40まで除外した。
- 原因：検索語の分割処理に問題があり、正しく評価できなかった。
- 修正：`query.strip().split()` で空白区切りの語を取り出すよう変更。
- 修正後の成果：10ページから6ページへ40%削減し、p.40を維持。
- 残る問題：第1回p.19や第3回p.51など、
  質問への直接的な必要性が低いページも追加された。

  モデルが2回検索したためシステム全体の費用は増加した。
- 回答時間の大幅な増加はAPI遅延の影響もあり得る。
- 最終測定の質問文には空白が1か所追加されており、
  また検索語・呼び出し回数も異なるため、厳密な統制比較ではない。
- 推定費用には埋め込みAPIと索引作成費用を含まない。

#### 考察

Graphの関連性フィルタは検索候補の削減には有効だったが、
単純なキーワード一致は言い換えに弱く、不要なページも残る。

検索ページ数の削減が、そのまま回答品質やシステム全体の
トークン数・費用の改善につながるわけではない。

今回の用途では基本RAGが低コストで正しい回答を出せており、
現時点では基本RAGを第一候補とする。

今後は候補の意味的な関連性評価、重要ページの再ランキング、
追加検索回数の制限などを検討したい。
