## 追加課題：実装

### 取り組んだこと
正常系・複数用語・講義要約・用語集にない語・宿題・講座外・指示の上書き・誤入力・存在しない回を含む独自評価セット10件を作成した。

`data/eval/my_cases.jsonl` に質問と期待するふるまいを記録し、第3回の学習支援エージェントで回答を生成した。Streamlitで人手評価を行い、Gemini 3.1 Flash LiteによるLLM採点と比較した。

### 最終結果
| 基準 | 一致率 |
|---|---:|
| 根拠 | 7/10 |
| 範囲 | 10/10 |
| ヒント | 10/10 |
| 分かりやすさ | 9/10 |
| 回の表示 | 10/10 |
| 総合 | 7/10 |
| Coverage | 100% |

要確認は0件、不一致は4項目だった。

### 不一致の分析
- #02 根拠：ランクrの典型値という、用語集にない補足情報の扱いで判断が分かれた。
- #03 根拠：AIエージェントとハーネスの役割を独自の比喩で説明することを許容するかで判断が分かれた。
- #03 分かりやすさ：人間は繰り返しが多く冗長と評価したが、LLMは簡潔と判定した。
- #05 根拠：用語集にないフローマッチングの一般的説明や講義回の推測を、どこまで許容するかで判断が分かれた。

#08の「回の表示」は、回答末尾に「第1回から第10回まで」が含まれるため、コード上はpassである。人手ラベルを訂正した結果、総合一致率は6/10から7/10になった。

### コード判定とLLM判定の使い分け
「第N回」という文字列の有無や、必須項目の存在など、明確な形式条件はコードによる判定が適している。高速かつ再現性が高いからである。

一方、用語集との意味的な整合性、役割の維持、説明の分かりやすさなどは、文脈の理解が必要なためLLMによる判定が適している。ただし、人手評価と照合し、見逃しを検証する必要がある。

今回、講座外の質問を正しく断っても末尾の第N回がないため不合格になる例があった。形式的な判定が実際の回答品質と一致しない問題であり、今後は拒否・聞き直しなどの回答を回の表示の例外とする改善が考えられる。

また、講義要約の採点画面には講義要点ファイルが表示されなかった。根拠を適切に評価できるよう、用語集だけでなく講義要点も参照欄に表示する必要がある。

## 追加課題：発展

### 調査対象
SWE-bench Verified

データセット：
https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified

作成方法：
https://openai.com/index/introducing-swe-bench-verified/

### ベンチマークの概要
実際のGitHubのIssueをもとに、AIエージェントがソフトウェアの不具合を修正できるか評価するベンチマークである。問題文と修正前のコードを与え、生成した修正パッチを適用してテストを実行する。

FAIL_TO_PASSは修正により失敗から成功へ変わるべきテスト、PASS_TO_PASSは既存機能が壊れていないか確認するテストである。両方を通過することが求められる。

### 確認した問題4件
公開データセットに掲載されている次の問題文を確認した。

1. astropy__astropy-12907：
   入れ子になった複合モデルのseparability_matrixが正しく計算されない問題。複数モデルの結合方法と内部処理を理解する必要がある。

2. astropy__astropy-13033：
   TimeSeriesの必須列をチェックする際、誤解を招く例外メッセージが出る問題。入力条件とエラー処理の整合性を確認する必要がある。

3. astropy__astropy-13453：
   ASCII表をHTMLとして出力する際、指定されたformatsが反映されない問題。オプションの伝播と出力テストを調べる必要がある。

4. astropy__astropy-13579：
   SlicedLowLevelWCSのworld_to_pixelに一貫性がない問題。座標変換とスライス処理を理解する必要がある。

いずれも単純な知識問題ではなく、既存コードを読んで原因を特定し、適切に修正する必要がある。自分だけで短時間に解くことは難しく、関連するPythonライブラリの知識とテスト環境が必要だと感じた。

### 作成人数と検証手順
OpenAIは93人のPython開発経験者と協力し、元のSWE-benchから1,699件を調査した。

各問題を3人が独立して評価し、問題文の曖昧さ、テストの妥当性、難易度などを確認した。重大な問題が指摘された例を除外し、500件を選別した。

### 今回の講義演習との比較
| 項目 | 第4回の評価セット | SWE-bench Verified |
|---|---|---|
| 件数 | 10件 | 500件 |
| 内容 | 学習支援AIの回答 | 実際のソフトウェア修正 |
| 作成・検証 | 講師が用意した例を人手とLLMで評価 | 93人が参加、各問題を3人が検証 |
| 採点 | 根拠・範囲・ヒント等のT/F判定 | コード修正後のテスト実行 |
| 主な課題 | 評価基準の主観性・曖昧さ | 問題文とテストの妥当性、環境再現性 |

### 追加調査と考察
OpenAIは2026年2月23日、SWE-bench Verifiedには依然として不適切なテストや問題記述が含まれ、学習データへの混入もあるため、最先端モデルの能力評価として使わなくなったと報告した。

参考：
https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/

大量の問題を専門家が確認しても、評価データ自体に欠陥が残る場合があることが分かった。

今回の講義では人間とLLMの判定の一致率を調べたが、そもそも人間のラベルや評価基準が妥当かという検証も不可欠である。評価セットの品質、採点基準、テスト環境、データ混入の管理まで含めて評価システムを設計する重要性を学んだ。
