### 1分で分かるMCPの構成

```text
利用者「第2回の要点を教えて」
          │
          ▼
エージェント / ホスト（app/mcp_agent.py）
          ├── モデル Gemini（どのツールを使うか選ぶ）
          └── MCPクライアント（サーバーと接続し実行依頼）
                  │
            MCPプロトコル
                  │
    ┌─────────────┼──────────────────┐
    ▼             ▼                  ▼
用語集サーバー   fetchサーバー       AWS Knowledgeサーバー
自作・ローカル   公開済み・ローカル   外部・リモート
stdio/command    stdio/command      HTTP/URL
    │
    ▼
Python関数（app/tools.py）
get_lecture_summary / search_glossary / make_quiz
```

- **モデル**：ツール名と引数を選ぶ。モデル自身がPython関数を実行するわけではない。
- **ハーネス／ホスト**：モデルの応答を受け、ツールの起動・接続・実行・結果返却を管理する。
- **MCPクライアント**：ホスト側でMCPサーバーと通信する機構。
- **MCPサーバー**：ツールの一覧、説明、引数スキーマを公開し、呼び出しに応答する。
- **`app/tools.py`**：実際の業務処理・検索などを行うPython関数。

**重要**：MCPは「モデルに与えるツールの接続方法を共通化するプロトコル」であり、「LLMそのもの」でも「データベース」でもない。どの資料を検索するか、何を実行するかはサーバーの実装次第である。（講義 pp.14–23、演習 pp.7–9）

## 02｜Part 1：ツールの種類と選び方

### 3つの代表的な入口

| 方法 | モデルから見えるもの | 長所 | 注意点 |
|---|---|---|---|
| Bash / CLI | シェルコマンドを実行する入口 | 既存コマンドを組み合わせやすい | 許可範囲が広くなりやすい。実行環境が必要 |
| 専用関数 / Function calling | 例：`search_glossary(query)` | 操作・引数・返り値を限定できる | ツール数が多すぎると選択が難しい |
| MCPツール | 共通の通信方式で公開された名前・説明・引数 | 他のクライアントから再利用しやすい | 接続先の信頼性と権限が重要 |

**判断手順**：①作業に使えるAPI・CLIはあるか → ②複雑な仕事なら専用ツールを作るか → ③別のエージェントやソフトとも共有するならMCPを検討 → ④APIがなければ画面操作を検討する。

同じ3操作を個別ツール3個にするか、Bash1個にするかでは、選択の簡単さ・自由度・安全性・呼び出し回数が変わる。「ツールを減らせば必ず良い」「万能Bashが常に最適」は誤り。（講義 pp.6–12）

## 03｜Part 2：MCPと権限管理

### MCPの基本用語

- **Tool discovery / ツール一覧取得**：使えるツールの名前、説明、引数をサーバーから受け取る。
- **Tool call / ツール呼び出し**：モデルが名前・引数を決め、ホストがMCPサーバーに実行依頼する。
- **Tool result / 返り値**：サーバーの実行結果をモデルへ戻す。
- **stdio**：クライアントがサーバープロセスを起動し、標準入力・標準出力で通信する。ローカル向け。
- **Streamable HTTP**：ネットワーク越しのMCP通信。既に動くリモートサーバーにURLで接続する。
- **JSON-RPC**：MCPメッセージの基本的な表現形式（`tools/call` など）。

### 認証と認可を混同しない

**認証（authentication）**は「誰であるか」、**認可（authorization）**は「何をしてよいか」。

たとえば社内資料検索では、利用者を識別しても、すべての資料を検索してよいことにはならない。サーバーはユーザーに許された資料のみを返すべきである。リモートMCPの認可では、OAuthのトークン・許可範囲を意識する。（講義 pp.24–26、82–83）

### なぜセキュリティが重要か

- **最小権限**：検索だけなら、削除・送信・投稿を許可しない。
- **秘密情報の管理**：APIキーやトークンをGitに保存しない。必要ならSecretsや安全な認証設定を使う。
- **プロンプトインジェクション**：取得したWebページやSlack本文に「別の操作を実行せよ」と書かれていても、利用者の指示に昇格させない。
- **外部への送信**：リモートMCPに渡した質問・引数は外部サービスへ送られ得る。
- **既製サーバーの点検**：提供元、ソース、README、対象ホスト、内部IP接続、robots.txtの扱いを確認する。

演習のfetchサーバーは、内部IPへのアクセスとrobots.txt無視を既定で許可していない。**エラー解消のために安全策を安易に無効化しない。**（講義 pp.15、29–31、演習 p.16）

## 04｜Part 3：モデルに使いやすいツールを設計する

モデルは、ツールの**名前・docstring（説明）・型ヒント・引数スキーマ**を読んで判断する。関数の中身は実行前にモデルへ自動表示されない。

**設計チェックリスト**

1. 名前から操作が分かるか（例：`make_quiz`、`get_lecture_summary`）。
2. docstringは「いつ使う」「何を渡す」「何が返る」を説明しているか。
3. 引数の型、必要条件、範囲（例：`lecture: int`）は明確か。
4. 応答は必要な情報だけか（長すぎる結果はトークンと費用を増やす）。
5. 大量データなら、**フィルタリング**と**ページネーション**を検討したか。
6. 失敗時には「何が悪いか」「次に何を指定すべきか」を返すか。
7. 危険な操作を実行できるようにしていないか。必要なら人間の承認を挟むか。

第6回の `make_quiz(99)` では、単に失敗するのではなく「存在しない講義回」と「利用可能な回」を返した。これはモデルの誤った作り話（架空の問題生成）を防ぐ一助となる。**ただし、今回の実装は入力値を厳密なバリデータで例外にするのではなく、説明文として返している。**（講義 pp.33–43、宿題 p.4）

## 05｜Part 4：ツールの性能を評価する

良い回答が出ても、ツールが正しく動いたとは限らない。**ツール呼び出し**と**最終回答**を分けて評価する。

| 評価観点 | 例 |
|---|---|
| ツール選択 | 正しいツールを選べたか |
| 引数の正確性 | `lecture=2` のように正しい値を渡したか |
| 実行結果 | ツールが正しい情報を返したか |
| 目的の達成 | 質問への回答・操作が実際に完了したか |
| 効率 | リクエスト数、トークン数、所要時間、費用 |
| 一貫性 | 同じタスクを複数回実行して安定して成功するか |

比較実験は、①タスク固定 → ②モデル固定 → ③ツール定義だけ変更 → ④成功率・費用を比較 → ⑤失敗事例を記録、という順序にする。講義では**BFCL**（関数呼び出し能力）、**τ³-bench**（対話とツール操作でのタスク完了）、**Pass^k**（繰り返し成功の一貫性）を取り上げた。（講義 pp.45–51）

## 06｜Part 5：Computer Useと画面操作

**優先順位の基本**：API → CLI → ブラウザのDOM操作 → 画像を見てマウス・キーボード操作。

- **API/CLI**：仕様が明確で再現性が高く、安定した自動化に向く。
- **DOM操作**：Webページの要素を指定してクリックする（例：Playwright）。
- **スクリーンショット操作**：GUIしかないアプリにも対応できるが、配置・状態変化に弱く、途中確認が必要。
- **Playwright**：安定した手順が分かった後、操作をコードにするのに使える。
- **OSWorld**：デスクトップアプリ操作でタスクを終えられるかを評価するベンチマーク。

画面操作を行うときは、操作前後の状態確認、例外時の停止、承認、監査ログを設計する。（講義 pp.53–62）

## 07｜Part 6：マルチエージェント

複数のエージェントに仕事を分ける方法には、独立並列、指揮役による分配、直列ワークフローなどがある。適するのは**互いに独立して進められる仕事**、専門性が異なる仕事、独立した検証役が効果的な仕事。

**注意**：エージェント数を増やすと、調整・トークン・待ち時間・誤りの伝播が増える可能性がある。担当ごとにテストが通っても、統合後のテストは別途必要。今回のGit統合後に21件のテストを再実行したのは、この考え方にも通じる。（講義 pp.63–72）

## 08｜Part 7：MCPとA2Aの違い

| 観点 | MCP | A2A（Agent2Agent） |
|---|---|---|
| 主な接続 | エージェント ↔ ツール・外部リソース | エージェント ↔ 別のエージェント |
| 主な目的 | 「この処理を実行して」 | 「この仕事を引き受けて進めて」 |
| 代表的な単位 | Tool名、引数、結果 | Agent Card、Message、Task、Artifact |
| 例 | 検索ツールでS3の文書を調べる | 他社の見積エージェントに見積作成を依頼する |

A2Aでは、①相手を見つける → ②依頼する → ③進捗を追う → ④成果物を受け取る、という流れを把握する。**MCPとA2Aは競合する二択ではなく、階層の違う仕組みとして併用できる。**（講義 pp.73–77）

## 09｜Part 8：失敗時はどこから調べるか

1. **データ**：取得する資料・根拠・ページ・権限が正しいか。
2. **ハーネス**：ツール選択、接続先、引数、出力形式、リトライ、プロンプトが正しいか。
3. **モデル**：上記が正しくても推論・選択が失敗するか。必要ならモデル変更。

モデルを替える前に、検索結果と `--trace` を見て、**どこで不具合が始まったか**を切り分ける。（講義 pp.78–81）

### 接続設定の完成形（今回のリポジトリ）

```json
{
  "mcpServers": {
    "glossary": {
      "command": "uv",
      "args": ["run", "python", "-m", "app.mcp_server"]
    },
    "fetch": {
      "command": "uvx",
      "args": ["mcp-server-fetch==2026.11.11", "--no-readability-js"]
    },
    "aws": {
      "url": "https://knowledge-mcp.global.api.aws"
    }
  }
}
```

- `command` がある場合：**Codespaces内**でプロセスを起動する。`glossary` と `fetch` が該当。
- `url` がある場合：既に動作中の**外部サーバー**に接続する。`aws` が該当。
- `uv` はPython環境での実行、`uvx` はツールパッケージを取得して実行するためのコマンド。
- `mcpServers` はこの**エージェントの設定形式**。どのMCPクライアントでも全く同じJSON形式という意味ではない。

### Python関数を公開する3行

```python
server.tool()(tools.search_glossary)        # 演習
server.tool()(tools.get_lecture_summary)   # 基礎
server.tool()(tools.make_quiz)             # 実装
```

`server.tool()(関数)` は、関数をMCPツールとして登録する。関数の型ヒントとdocstringがツールの説明に使われる。エージェントは起動時にサーバーから公開ツールの定義を取得するので、ツール追加のたびに `app/mcp_agent.py` を変更する必要はない。（演習 pp.10–13、宿題 pp.2–4）
